# 07 · 性能画像与测量方法

## 1. 生产实测（2026-09-23，INT8 表 + MTP4 + 1M 档 + 210 W）

| 指标 | 实测 | 备注 |
|---|---|---|
| decode（短上下文热态） | **90 ~ 130 tok/s** | 引擎日志 `Avg generation throughput`，并发 1~3 |
| decode（32K~256K 上下文） | 73 ~ 87 tok/s | 见 §3 与手册对比 |
| 预填充峰值 | **8,662 tok/s** | 单发 32K；`Avg prompt throughput` 峰值 |
| TTFT（32K） | 4.25 s | 流式，按"任意第一个增量" |
| MTP 平均接受长度 | **3.74** | `1 + accepted/drafts` = `1 + 313601/114240`（快照见 `tools/metrics-snapshot.txt`） |
| 前缀缓存累计命中率 | **95.3%** | `hits_total / queries_total` = 48.43M / 50.90M |
| GPU KV 池 | **1,224,366 token**（18.16 GiB） | @1M 上下文并发 1.17×；@262144 档为 1,464,390 / 5.59× |
| 显存 | 39.6 + 40.3 GiB / 卡 | `gpu-memory-utilization 0.95` |
| 冷启动 | **约 4 分钟** | 见 §2 拆解 |
| 稳定性 | Xid = 0 | 含 245760 token 长上下文压测 |

## 2. 冷启动耗时拆解（三次一致）

```
wrapper → PLE 表挂载            93 ~ 109 s
权重加载（每个 PP rank 单线程）  138 ~ 180 s   ← CPU-bound，与页缓存无关（P25）
init engine（profile+KV+图）    表冷 226.8 s / 表热 33 ~ 42 s
compile                         0.49 ~ 20.5 s（AOT 缓存命中时几乎为 0）
CUDA 图捕获                     4 ~ 18 s（0.20 ~ 0.24 GiB）
```

**提速优先级**：`保 PLE 表驻留 >> 一切其他`。
表热时总启动 5.4~5.9 min → 用 INT8 + 驻留后可到 ~3.5 min。
**已实测否定**的手段：多线程加载器（慢 20.4%，P26）、BF16 档预热页缓存（结构性无效，P27）、调 `read_ahead_kb`（P28，只有 0→128 是大跳变）。

## 3. 与官方手册（同型号 2×170HX 参考机）对比

同方法：自然文本 + **每轮换盐防前缀缓存** + 流式测 TTFT。

| 档位 | 手册 decode | 本机 decode | 达成 |
|---|---|---|---|
| 32K | 116.9 | 79.9 →（09-25 复测 87） | 68~74% |
| 128K | 104.8 | 75.2 → 73 | 70~72% |
| 256K | 116.5 | 76.3 → 83 | 65~71% |

| 档位 | 手册预填充 | 本机 | 达成 |
|---|---|---|---|
| 32K / 128K / 256K | 7361 / 7725 / 7229 | 6982 / 7207~7334 / 6882 →（复测含 7470） | **94~101%** |
| TTFT 32K/128K | 4.36 / 16.60 s | 4.25~4.66 / 18.19 s | **92~101%** |

手册自报轮间噪声 ±20~25%，30% 的 decode 差距**超出噪声带，是真的**。

## 4. decode 差距归因（结论：主机平台代差，软件侧无空间）

**已逐一排除（都有实据，别重复排查）**：

| 嫌疑 | 判据 | 结论 |
|---|---|---|
| INT8 表 / 内存不够 | PLE 查表 prefill 同样要走，若是短板 prefill 必一起慢；但 prefill 达 94~101% | **排除** |
| 配置差异 | capture_sizes / PP 26,22 / seqs / block1616 / mamba float32 / moe auto / mtp4 逐项一致，KV 池还比手册大 4.6% | **排除** |
| 显存带宽 | decode 期 `dmon` 的 `mem%` 仅 14~42% | **排除** |
| 磁盘 I/O | 服务期读 0 MB/s、majflt≈0 | **排除** |
| PCIe 位宽降级 | 09-15 曾见 GPU1 `x4`，09-25 恢复 `Gen2 x16` 满宽后**复测 decode 百分比不变** | **证伪** |
| 功率墙 | 限 200 W 时 GPU1 撞墙掉 1~2% 频率；放到 250 W decode 无实质变化 | 次要（~1~2%） |
| PLE 是瓶颈 | 持有 47 GB 表的进程 decode 期 CPU 仅 28.6%（不到 1/3 核） | **排除** |

**唯一自洽的解释 = 主机平台代差**：
decode 每步都含 ①CPU 侧 PLE n-gram 查表（走 torch CPU 算子，受**内存带宽/延迟**支配）
②PP2 跨卡激活中继（P2P=CNS 时走 host SHM，CPU 参与）。
本机 E5 v4 + **4 通道 DDR3-1866，STREAM 实测 50.3 GB/s**；手册机是 ≥128 GB 的更新平台（8 通道 DDR4 量级）。
prefill 是 8192-token 大块、GPU 吞吐主导，所以不受影响 —— **这正好解释了"只 decode 慢"的指纹**。

> **推论**：想把 decode 追到手册水平，需要换主机平台（内存带宽/延迟），不是调 vLLM。
> 同类硬件的公开对照：`ChinaBoy0618/170hx-qwen3.8-27b-fullstack`（4×170HX + 256 GB RAM）也在做 KV 分级缓存，
> 其容量铁律（内存档必须大于 GPU 池才有收益）与本仓库 `docs/05#D组` 的结论一致。

## 5. 测量方法（两个必须记住的坑）

1. **本实例没有 `/v1/tokenize`**（404）。要构造指定长度 prompt 只能用**字符→token 比率标定**：
   先发一次已知长度的请求读 `usage.prompt_tokens`。本模型中文 ≈ **0.53 tok/字符**（换语言要重标）。
2. **这是思考模型**：流式时首个增量在 `delta.reasoning_content`，**不是** `delta.content`。
   TTFT 必须按"任意第一个增量"算，只等 `content` 会永远拿不到（本项目为此崩了两次 `TypeError`）。
3. 测缓存必须**每轮换盐**，否则第二次开始全命中，测出来的是缓存速度不是算力。
4. **测量纪律**：同档位第 1 个样本系统性偏低（页缓存/图预热），必须丢前 1~2 个样本取热值；
   **绝不可把不同协议/不同样本数的两组数字放进同一张表比较**（本项目曾因此错报"k=3 快 14%、手册错"）。

```bash
python3 scripts/bench-fnx.py 32768,32768,32768 512      # 三档 32K prompt，各生成 512 token
python3 scripts/bench-fnx.py 131072 256 --url http://<部署机>:18420/v1
```

## 6. 吞吐/延迟的口径提醒

- `/metrics` 的增量会被并发请求污染，看**累计命中率**没问题，看"某一时刻"要用 trace。
- 客户端看到的 `cached_tokens` 需要 `--enable-prompt-tokens-details`，否则恒 `null`（P23）。
- 前缀缓存有两个固有折扣（异步提交 ~20 s + 每请求末块 ≤1616 token 永不写入，P24）——
  所以"重发只命中 90%"是正常的，不要当成故障去调参。

## 7. 2026-09-29 定案：YaRN 无罪与 KVOFF 退役（同协议补测）

**背景**：参考机（18432 路线，stock vLLM 0.30.0）自报 MTP 接受率 65.7%，本机长期 ~30%。头号嫌疑 = YaRN×4（1M 副本）压低接受率。

**A/B（同协议：32K prompt ×3、生成 512 token、temperature=0、丢弃冷样本）**

| 档位 | decode 中位 | 接受长度 | 逐位接受率 |
|---|---|---|---|
| 1M YaRN×4（block1680/K5） | 93.7 tok/s | 2.51 | 30.2% |
| 原生 262144（同 K5，KVOFF=0） | 97.4 tok/s | 2.53 | 30.5% |

**结论**：
1. **YaRN 无罪** —— 接受率差在噪声内，1M 上下文对投机几乎零代价，保留 1M 档。
   参考机 65.7% 属 **prompt 协议差异**（说明文/复述型天然偏高）；跨机接受率不对齐 prompt 构造与 temperature 不可比。
2. **KVOFF 退役** —— 生产 21.5 h `external_prefix_cache_hits_total=0`（GPU 前缀缓存自给 ~90% 命中），
   代价是钉 ~107 GiB 物理内存，外加 PP2 拷贝路径两种故障模式（09-23 抢占崩 / 09-24 卡死）。
   三处缺省（inner 脚本、server.js base+fallback、index.html 弹窗）已全部翻为**关**，
   补丁脚本 `tools/patch-kvoff-default-off-0929.py`（幂等、`--revert` 可回滚、`node --check` 门禁）。
   复活条件：再现超出 GPU 池（1.19M token）的长多轮重发；开启时遵守 09-23 组合（PLE heap、不 drop_caches、容量 ≥ GPU 池）。
3. **PLE 精度统一** —— envfile 曾漂移 BF16+heap，三源缺省为 INT8+heap（49.2 GiB 不可回收 vs 95.4 GiB，decode 实测持平）。
   已统一 INT8+heap；产物不随仓库分发，用 `python3 scripts/quantize_ple.py --model <W4A16目录> --out /media/ll/data/ple`
   再生（约 10 分钟，可断点续传，`--verify-only` 做字节级自检）。
